## 1. DOORMAN deleted far more than it was asked to - DONE

**Found, fixed and deployed 2026-08-30 (commit 243e1d79a, live 278a3bb75).**

The live volume confirmed the damage: `/app/data/bbs/Doors` did not exist at
all, only `Doors.info` beside it, while `Commands/BBSCmd` still held its 365
`.info` files - a board that listed doors none of which could run, DOORMAN
included, because DOORMAN lives in `Doors/door-manager`.

The cause was the repo-view uninstall:

    const abs = path.join(PROJECT_ROOT, e.install_dir);
    if (fs.existsSync(abs)) fs.rmSync(abs, { recursive: true, force: true });

with nothing checking the value. `install_dir` is written as
`Doors/${command}`, so a record with no command gives `Doors/` and the
recursive force-delete takes every door on the board. The backend's own
delete path (`amigaDoorManager.deleteTypeScriptDoor`) already had this guard;
DOORMAN's did not.

`resolveDoorInstallDir` now resolves a stored `install_dir` to a deletable
path only when it lands strictly inside `<root>/Doors/`. Eight tests, one per
shape that must never be deleted.

**The doors are back**: the deploy's door sync restored them from the image -
106 directories, DOORMAN among them - and the guard is confirmed running in
the live `dist/app.js`.

The user was deleting doors through DOORMAN on the live server. DOORMAN itself
disappeared, and it looks like every door went with it. The user did not delete
DOORMAN.

First step: the server logs. Live host `root@89.167.21.154`, key
`~/.ssh/hetzner_deploy`, port 22. Establish from the logs what the delete path
actually removed and how the selection became "everything" - do not theorise
from the code before reading what happened. Note that a deploy replaces the
container, so pull the logs before anything else forces a restart.

Then: what is recoverable, and from where. `Commands/BBSCmd/*.info` is the
authority for a door's existence; the door binaries live under `Doors/`.

## 2. Show a live log in the right panel while doors are being deleted - DONE

Commit 97c94f0a4. Every path is listed, one per line: `[OK]` for removed,
`[SKIP]` for something already gone, `[FAIL]` with the reason when the guard
refuses. ASCII markers, because this renders in a BBS terminal.

Original request:

DOORMAN and DOORREPO both delete without showing the sysop what they are
touching. Every path that removes a door must name each file as it goes, in the
right-hand panel, so a run that starts removing the wrong thing is visible while
it happens rather than afterwards.

Related to item 1 and part of making that path bullet proof: the log is the
evidence, and a confirmation that names what will be removed is the guard.

## 3. Deleting a door in DOORMAN leaves it in the list - DONE

Commit 278a3bb75. The uninstall fired `void refreshDoorRegistry()` and redrew
in the same tick, so the list was rebuilt from the still-cached registry with
the deleted door still on it. It now waits for the reload.

Original report:

The list is not refreshed after a successful delete, so the door the sysop just
removed is still on screen.

## 4. GMASTER shows no zone meter in zone mode - DONE

Commit 39f71ff1d. The meter was built on every frame and appended to the STATS
box, which is eight rows with a border - six usable lines, and Level, Lines,
Score, Combo, Grav and PPS already filled all six, so the meter was drawn past
the bottom of the box. It has its own box now, shown only in zone mode, with
the percentage, a ten-cell bar, and whether the zone can be entered yet.

Original report:

Zone mode renders without its meter.

## 5. Door installation must take the command from the .info file - DONE

Commit abced735b. Door archives ship Commands/BBSCmd/<COMMAND>.info, and that
file carries TYPE, LOCATION, STACK, PRIORITY and NAME. The install now finds
it, moves the door to that command, and installs the archive's own icon
instead of a synthesised four-line one. It will not rename onto a command that
already exists, and an archive with no command icon behaves exactly as before.

Original request:

Installing through DOORMAN or DOORREPO asks the sysop to choose the BBS command
(and the other tooltype values). It should read them out of the door's own
`.info` file instead. The sysop being able to choose is how a door ends up
installed under a command that does not match what it ships with.
